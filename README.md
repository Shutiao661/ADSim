# ADSim — 自动驾驶行为决策仿真及数据分析平台

针对自动驾驶路测中「极端场景（Corner Case）难复现、行为决策算法验证成本高」的痛点，
构建的一套集**路测数据清洗、仿真场景生成、Planning 算法验证**于一体的工具链。

## 核心特性

| 能力 | 说明 |
|------|------|
| **ROS Bag 解析** | 自己实现的 ROS Bag v2.0 格式读写器。流式读取、零拷贝访问，内存占用与文件大小无关；**支持 bz2/lz4 压缩 Chunk**，格式已与 ROS 官方 `roslz4` 双向交叉验证 |
| **多线程数据管道** | 内存池 + 无锁环形缓冲 + 线程池三层配合，解包、解码、降噪各阶段重叠执行，天然背压 |
| **时间对齐与降噪** | 多传感器时间对齐（连续量线性插值、航向走最短路径）；点云体素降采样 + 统计离群点去除 + RANSAC 地面分离；GPS 卡尔曼滤波 + 离群点门控 |
| **行为决策** | 有限状态机（模式层）× 行为树（任务层）的双层结构，避免纯状态机的状态爆炸与纯行为树的全局约束缺失 |
| **路径规划** | Delaunay 三角剖分 → Voronoi 路线图绕障 → B 样条拟合 → 自研 LM 求解器数值优化，把曲率压进车辆可行范围 |
| **仿真内核** | 二维运动学自行车模型 + 车道网络 + 危险工况库，确定性可复现，可对同一场景横向对比不同算法 |
| **可视化** | 零依赖 SVG 出图 + HTML 报告；轨迹按曲率着色，曲率突变一眼可见 |
| **场景打标** | 可量化交互特征的规则打标（始终可用）+ LLM 语义增强（可选），从海量数据中筛出高价值片段 |

**核心库为零外部依赖的纯 C++17**，任何环境下 `cmake && make` 即可构建运行。
`adsim_viz`（Qt 交互前端）与 LLM 的真实 HTTP 通道已验证可在装有 Qt5 / libcurl 的机器上构建运行；
Ceres / CARLA / ROS 的接入代码同样按真实 API 编写，本机未安装故未验证。

## 快速开始

### 构建

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release
cmake --build build -j$(nproc)
```

### 运行测试

```bash
cd build && ./bin/adsim_tests
```

### 典型用法

```bash
# 1. 生成合成路测数据（含 GPS 跳点与点云离群点）
#    可选压缩：--compression=none|bz2|lz4
./bin/generate_bag --output=demo.bag --duration=20 --lidar-points=20000

# 2. 查看 bag 元信息
./bin/adsim_cli probe demo.bag

# 3. 跑完整数据管道：解析 → 时间对齐 → 降噪 → 落盘
./bin/adsim_cli pipeline demo.bag --out=clean.bag

# 4. 列出内置危险工况
./bin/adsim_cli scenarios

# 5. 运行场景并出图
./bin/adsim_cli scenario LeadBrake --report=report.html --svg=overview.svg

# 6. 路径平滑：对比优化前后的曲率
./bin/adsim_cli smooth --svg=smooth.svg

# 7. 性能基准
./bin/adsim_cli bench --frames=400 --points=30000
```

### 压缩 Chunk 支持

同一份数据以三种压缩方式写入，**管道解出的结果逐项完全一致**
（700 消息、0 解码失败、757500 点 → 42156 点），压缩层对上层透明：

| Chunk 压缩 | 文件大小 | 管道吞吐 | 相对未压缩 |
|---|---|---|---|
| none | 12.56 MB | 329.49 MB/s | 100% |
| **lz4** | 12.27 MB | **251.43 MB/s** | **76%** |
| bz2 | 11.24 MB | **7.14 MB/s** | **2%** |

**bz2 的解压开销把整个管道拖慢了 46 倍**——它只多省下 1MB，却几乎吃掉了全部吞吐。
实车数据若追求处理效率应当选 lz4；bz2 只适合归档存储。

复现：

```bash
generate_bag --output=demo.bz2.bag --compression=bz2
generate_bag --output=demo.lz4.bag --compression=lz4
adsim_cli pipeline demo.lz4.bag
```

**格式正确性经独立实现交叉验证**（不是自己验自己）：

| | 验证方式 | 结果 |
|---|---|---|
| LZ4 | 与 ROS 官方 `roslz4`（`ros_comm/utilities/roslz4`）双向对撞 | 双向均逐字节一致，**压缩产物大小完全相同** |
| bz2 | 与 Python 标准库 `bz2` 模块双向对撞 | 双向均逐字节一致，压缩产物大小完全相同 |

交叉验证的具体做法见 [docs/algorithms.md](docs/algorithms.md#压缩格式的交叉验证)。

### 路径平滑（曲率突变治理）

在半径 30m 的圆弧上叠加 σ=0.18m 横向噪声，设定曲率上限 0.05 1/m。
项目实现了**两个可切换的平滑后端**，可用 `adsim_cli smooth` 直接对照：

```
后端                点数     最大曲率   曲率变化率     最大偏移     耗时(ms)  满足约束
------------------------------------------------------------------------------------
bspline              200       0.0410       0.0074        2.298         2.94        是
optimization          41       0.0544       0.0643        0.277       420.12        否
```

两者不是替代关系而是**真实的取舍**：

| | B 样条拟合 | 数值优化 |
|---|---|---|
| 曲率变化率 | **低 8.6 倍**（更平滑） | 较高 |
| 相对原路径偏移 | 2.30 m（大 8.3 倍） | **0.28 m**（更贴合） |
| 耗时 | **快 143 倍** | 慢 |
| 适用场景 | 生成全新的平滑路径 | 精确贴合车道行驶 |

2.3m 的偏移对 3.5m 宽的车道足以导致压线，因此 `PathPlanner::SmoothingBackend::kAuto`
**以偏移为判据**自动裁决：B 样条偏移超阈值就退回数值优化，并记录退回原因。

**换上 Ceres 后这个对比会变**（同上问题）：

```
bspline              200       0.0410       0.0074        2.298         2.46        是
optimization          41       0.0505       0.0643        0.285        14.23        是
```

优化后端变得既满足约束、又只慢 6 倍（而非 170 倍），B 样条的优势收窄到只剩平滑度。
**后端选择与求解器选择是耦合的**——这也是把两者都做成可切换的收益之一。

复现：

```bash
adsim_cli smooth                      # 两个后端对照
adsim_cli smooth --backend=bspline    # 只跑 B 样条
adsim_cli smooth --svg=smooth.svg     # 输出对照图
```

### 决策算法的实际收益

同一场景、同一仿真内核，只替换策略：

| 场景 | 完整策略（FSM + 行为树 + 路径优化） | 基准（纯路径跟踪） |
|------|-----------------------------------|------------------|
| 前车急刹 | 碰撞 0，近失 0，最小间距 **4.17 m**，TTC 1.23 s | **碰撞 1**，间距 0 m |
| 旁车加塞 | 碰撞 0，近失 0，最小间距 **9.53 m** | **碰撞 1**，间距 0 m |
| 行人横穿 | 碰撞 0，近失 1，最小间距 **1.12 m** | **碰撞 1**，间距 0 m |

三组对照中，缺少决策层的基准策略全部发生碰撞。这量化了「行为决策」本身
（而非更好的控制器）带来的收益——它对应简历中"仿真平台复现高价值场景、
支撑算法回归"的价值主张。

复现方式：

```bash
adsim_cli scenario LeadBrake --policy=planning
adsim_cli scenario LeadBrake --policy=cruise     # 对照组
```

## 架构总览

```
                        ┌─────────────────────────────────────┐
   实车数据 ──► bag ──► │  数据管道                            │
                        │  解包 → 解码 → 时间对齐 → 降噪 → 落盘 │
                        └──────────────┬──────────────────────┘
                                       │ 清洗后的数据
                                       ▼
                        ┌─────────────────────────────────────┐
                        │  仿真内核                            │
                        │  世界模型 + 车辆模型 + 场景库         │
                        └──────────────┬──────────────────────┘
                                       │ 每步调用
                                       ▼
    ┌──────────────────────────────────────────────────────────────┐
    │  策略（IPolicy）                                              │
    │                                                              │
    │   感知 ──► 决策 ──────► 路径规划 ──────► 速度规划 ──► 控制    │
    │           FSM + 行为树   Delaunay/B样条   曲率/跟车/舒适      │
    │                          + LM 优化                            │
    └──────────────────────────────┬───────────────────────────────┘
                                   │ 仿真结果
                                   ▼
                        ┌─────────────────────────────────────┐
                        │  可视化 + 打标                       │
                        │  SVG / HTML 报告 / 交互场景标注       │
                        └─────────────────────────────────────┘
```

**关键设计**：仿真内核通过 `IPolicy` 接口调用被测算法，内核本身不做任何决策。
这使得「同一场景、不同算法」的横向对比成为可能——这正是仿真平台作为回归测试
基础设施的核心价值。

## 模块详解

### 1. 数据管道（`datapipeline/`）

| 文件 | 职责 |
|------|------|
| `RosBagFormat` | Bag v2.0 格式原语：记录/头部字段编解码、时间编码 |
| `RosBagReader` | 流式读取器。按 Chunk 载入并复用同一缓冲区，内存与文件大小无关 |
| `RosBagWriter` | 写入器。Chunk 缓冲累积 + 关闭时补写完整索引区，产出 ROS 兼容 bag |
| `MessageCodec` | `NavSatFix` / `Odometry` / `PointCloud2` 的真实 ROS 序列化格式编解码 |
| `TimeAligner` | 批量与流式两种对齐器。航向插值走最短路径，避免 ±π 附近跳变 |
| `PointCloudFilter` | 距离裁剪 → 车体剔除 → 体素降采样 → 统计离群点去除 → RANSAC 地面分离 |
| `GpsFilter` | 常速度模型卡尔曼滤波 + 卡方门控 + 自适应观测噪声 |
| `DataPipeline` | 管道编排：读取线程 → 环形缓冲 → 派发 → 线程池 worker |

### 2. 规划决策（`planning/`）

| 文件 | 职责 |
|------|------|
| `Fsm` | 驾驶模式状态机。转移带守卫与动作，可导出 Mermaid/DOT 状态图 |
| `BehaviorTree` | 行为树。Sequence/Selector/Parallel + 五种装饰节点，支持中断与恢复 |
| `DecisionMaker` | 双层决策：状态机定模式，行为树定任务；输出具体驾驶动作 |
| `geometry/Delaunay` | Bowyer-Watson 三角剖分 + Voronoi 路线图（绕障路径搜索）⚠️ 见下 |
| `geometry/Spline` | 三次 B 样条（De Boor）+ 最小二乘拟合 + 曲率约束平滑 |
| `geometry/CurveFit` | 多项式拟合、RDP 抽稀、弧长重采样等路径预处理工具 |
| `optimizer/NonlinearSolver` | 自研 LM/高斯-牛顿求解器，接口与 Ceres 同构 |
| `optimizer/PathOptimizer` | 路径平滑的四项代价模型 + 外层约束迭代 |
| `PathPlanner` | 车道采样 / 换道（五次多项式）/ 双平滑后端 / Voronoi 绕障 ⚠️ |

> ⚠️ **Voronoi 绕障尚未接入主流程**：`PathPlanner` 的绕障分支需要障碍物离散点集
> （`PathPlanningRequest::obstacle_points`），而项目目前没有真正的感知模块去产生它，
> 因此 `avoid_obstacles` 在端到端流程中始终为 false。三角剖分与路线图本身有完整
> 单元测试（见 `test_geometry.cpp`），但**在生产路径上尚未被执行过**。
> B 样条模块此前也是同样情况，现已接入 `PathPlanner` 作为可切换的平滑后端。
| `SpeedPlanner` | 曲率限速 + IDM 跟车 + 加速度/jerk 可行性修正 |
| `PlanningPolicy` | 串联全流程，实现 `IPolicy` 接入仿真；纯跟踪横向控制 |

### 3. 仿真（`sim/`）

| 文件 | 职责 |
|------|------|
| `VehicleModel` | 运动学自行车模型，圆弧精确积分（非欧拉近似） |
| `World` | 车道网络、静态障碍、动态物体；点→车道的投影与坐标系变换 |
| `SimEngine` | 固定步长推进、OBB 碰撞检测（SAT）、TTC 计算、安全事件记录 |
| `Scenario` | 五个危险工况 + 场景注册表 |
| `CarlaBridge` | CARLA 0.9.x 真实 API 桥接（可选依赖） |

### 4. 可视化与打标（`viz/`、`agent/`）

| 文件 | 职责 |
|------|------|
| `SvgCanvas` | 世界坐标 → SVG 的绘图画布，轨迹按曲率着色 |
| `SimVisualizer` | 仿真俯视图、时序图、HTML 报告、回放对比 |
| `QtVisualizer` | Qt 交互式复盘前端（可选依赖） |
| `LlmClient` | LLM 客户端抽象 + 离线桩实现 + libcurl 真实实现（可选依赖） |
| `ScenarioTagger` | 交互特征提取 → 规则打标 → LLM 语义增强 |

### 两个求解器后端的实测对比

同一问题（41 点圆弧 + σ=0.18m 噪声，曲率上限 0.05 1/m）：

| | 内置 LM | Ceres 2.2.0 |
|---|---|---|
| 迭代次数 | 500（达上限，未收敛） | **3（收敛）** |
| 最大曲率 | 0.417 → 0.054 (1/m) | 0.417 → **0.050 (1/m)** |
| 最大曲率变化率 | 0.747 → 0.064 (1/m²) | 0.747 → 0.064 (1/m²) |
| 最大偏移 | 0.295 m | 0.303 m |
| 耗时 | 442.68 ms | **14.54 ms** |

Ceres 快约 30 倍且能精确满足曲率约束。差距的主因是**曲率残差的雅可比求法**：
内置后端为避免手写 Menger 曲率的解析导数，在残差块内部用中心差分（每个块每次
求雅可比要多算 6 次残差）；Ceres 用自动微分直接得到精确雅可比。

这个对比正是"接口与 Ceres 同构"这一设计的意义所在——两个后端求解同一个数学
问题，代价函数定义一行不改，但性能与精度差一个数量级。内置后端的价值在于让工程
在无 Ceres 的环境下依然完整可用、可测试。

## 设计取舍

工程中几个值得说明的决策：

**为什么自研求解器而不是直接用 Ceres？**
核心库的目标是「任何环境下可构建可验证」。Ceres 是重型依赖（需要 Eigen、glog、gflags），
在没有它的机器上整个项目就无法编译，也就无法跑回归测试。因此把求解器接口设计成与
Ceres 同构，默认用自带实现，装了 Ceres 再切换——代价函数定义一行不用改。

这个设计经实测验证：Ceres 比自带实现快约 30 倍且能精确满足曲率约束（见上表）。
两者求解的是同一个数学问题，差距来自雅可比的求法而非问题建模。换句话说，
自带实现是一个**可工作的下界**，而不是一个"够用的替代品"——它的存在是为了让
工程在任何环境下都能跑起来并跑回归，一旦有 Ceres 就应当切换。

**为什么用二维仿真而不是直接上 CARLA？**
CARLA 需要 GPU 与数十 GB 资源，单次仿真耗时以秒计，无法支撑「数百个场景批量回归」。
行为决策与路径规划所需的全部几何信息（车道拓扑、曲率、可行驶区域）在二维平面上都能
精确表达，而吞吐量提升数个量级。CARLA 桥接作为可选项保留，用于最终的高保真验证。

**为什么内存池要用线程本地缓存？**
消息载荷按 Chunk 复用缓冲区、无法跨线程持有，必须拷贝。16 线程下逐条 `malloc`
会因锁竞争成为瓶颈。线程本地缓存一次从中心链表批量取块，把锁竞争降低 1~2 个数量级。
实测命中率见 `adsim_cli bench` 输出。

**为什么离线点云处理不用 GPU？**
体素降采样与统计离群点去除都是访存密集型而非计算密集型，CPU 多核并行已能到
200+ MB/s，引入 CUDA 会带来部署复杂度而对吞吐提升有限。

**为什么 GPS 滤波要有自适应噪声？**
实车数据的 `fix_type` 标注与实际噪声经常不符（接收机报 RTK 固定解，实际水平误差
仍有米级）。若完全相信质量加权，观测噪声会被压到极小，滤波器过度自信，反而把大量
正常观测当成离群点拒掉——实测中该失效模式会拒掉 96% 的正常数据。
