# 算法说明

本文记录各核心算法的原理、**参数是如何标定的**，以及在实测中发现的问题与修正。
后者往往比原理本身更有参考价值。

---

## 1. 时间对齐

### 问题

实车各传感器独立打时间戳（Lidar 10~20Hz、GPS 10Hz、底盘 CAN 50~100Hz），
硬件触发延迟与传输抖动使它们无法按序号配对。

### 做法

以点云流为参考节拍，其余传感器向它对齐：

- **离散量**（点云）：只能取最近邻，插值没有物理意义
- **连续量**（位姿、速度、经纬度）：线性插值
- **航向角**：按最短路径插值

### 关键细节：航向插值

直接对两个角度做线性插值是错的。当航向从 +179° 转到 −179° 时，实际只转动了 2°，
但朴素插值会走 358° 的长弧，中间点被拉到 0° 附近。

正确做法是先归一化角差到 (−π, π]，再插值：

```
θ(t) = normalize(θ₀ + normalize(θ₁ − θ₀) · t)
```

### 关键细节：等距取点

`nearestIndex` 在恰好等距时取**更早**的样本。这是刻意的选择：在线场景下
「不多看未来的数据」比「少滞后一点」更重要，且让结果可确定复现。

## 2. 点云降噪

处理链：距离裁剪 → 车体剔除 → 体素降采样 → 统计离群点去除 → RANSAC 地面分离。

### 体素降采样

取每个体素内所有点的**质心**而非第一个点。质心对噪声更鲁棒，且结果与输入点序无关。

### 统计离群点去除（SOR）

对每个点计算其 k 近邻的平均距离，剔除平均距离超过 `μ + ratio·σ` 的点。
k 近邻查询用均匀网格做空间索引，把朴素 O(n²) 降到接近 O(n)。

环形扩展搜索的终止条件：访问完第 r 环后，所有未访问单元到查询点的距离
至少为 `r × cell_size`，因此当第 k 近的距离不超过该下界时即可安全终止，
结果与暴力搜索完全一致。

### 实测发现的两个坑

**坑一：邻域不足的点会污染统计量。**
某些点周围凑不满 k 个邻居（本就是孤立点）。如果按实际邻居数取平均，
孤立点的平均距离反而偏小而被误留；如果直接置为极大值，又会撑爆全局均值与标准差。
正确做法是把这类点**排除在统计之外**，并直接判为离群点。

**坑二：均匀点云上 SOR 会系统性剔除边界点。**
边界点的平均近邻距离天然大于内部点（邻居只分布在一侧），
在均匀栅格上约有 13% 的边界点会被判为离群。这**不是缺陷而是该算法的固有特性**。

因此验收标准应当落在「内部点不得被误伤」上，而不是「整体保留率」。
`test_pipeline.cpp` 中的 `统计离群点去除保留内部点` 正是这样断言的。

## 3. GPS 卡尔曼滤波

### 模型

常速度模型，状态 `x = [px, py, vx, vy]ᵀ`，观测 `z = [px, py]ᵀ`。

### 离群点门控

新息的马氏距离平方服从 2 自由度卡方分布，超过阈值即判定为跳点。
阈值 9.21 对应 99% 分位数——这同时意味着**约 1% 的正常观测会被固有地判为异常**，
这是门控机制无法回避的代价。对误拒更敏感的场景可放宽到 13.82（99.9%）。

### 实测发现：纯质量加权会导致灾难性误拒

最初按 `fix_type` 与 `hdop` 对观测噪声加权：RTK 固定解的方差取基准的 1%。
结果**96% 的正常观测被拒**。

原因是实车数据的 `fix_type` 标注与实际噪声经常不符：接收机报 RTK 固定解，
实际水平误差仍有米级。观测噪声被压到极小后，滤波器过度自信，
收敛期的真实滞后被当成离群点拒掉；而拒绝又使状态停止更新、滞后进一步扩大，
最终「锁死」在错误预测上再也拉不回来。

### 修正一：诚实的先验协方差

初速度完全未知——可能静止，也可能在高速行驶。原先给 σ_v = 3.16 m/s 是过度自信的，
应给到 20 m/s 量级。这样收敛期的暂态滞后能体现在协方差里，被门控正确容忍。

### 修正二：自适应观测噪声

用新息的二阶矩直接反推观测噪声：

```
E[y₀² + y₁²] = P₀₀ + P₁₁ + 2R   ⇒   R = (E[y²] − P₀₀ − P₁₁) / 2
```

**注意：这里刻意不用「NIS 偏离 2 就按比例缩放 R」的反馈式做法。**
该映射是递减的，在不动点处斜率约为 −1，实际表现为持续振荡而非收敛——
这是实测中踩过的坑。

上限用**有物理意义的值**（400 m²，对应 20 m 标准差）而不是「基准 R 的若干倍」：
质量加权把基准压到 0.01 m² 量级时，即便放大 25 倍也只有 0.25 m²，
仍远低于真实噪声，自适应机制会被这个相对的帽子卡死。

### 修正三：拒绝时重新打开不确定度

门控的前提是滤波器处于稳态。连续拒绝说明预测与观测系统性不符，
此时适度放大位置协方差（上限 100 m²），让门控重新打开。

### 标定结果

过程噪声 `process_noise` 经实测扫描标定为 **5.0**（白噪声加速度功率谱密度）。
扫描数据显示：过小则跟不上真实运动、误差反而大于原始观测（q=0.1 时 RMSE 2.52 vs 原始 2.68）；
过大则退化为直通、失去平滑作用（q=50 时 RMSE 2.13）。

修正后：接受率 96~97%，滤波后 RMSE 全面优于原始观测。

## 4. 行为决策

### 双层结构

| 层 | 职责 | 为什么需要 |
|----|------|-----------|
| 有限状态机 | 决定当前的**驾驶模式** | 模式互斥、有驻留时间、切换需被审计 |
| 行为树 | 决定模式内的**执行策略** | 可组合、可重试、可在运行中被中断 |

纯状态机在「换道」这类带多个子步骤的行为上会产生状态爆炸
（换道判断/换道中/换道失败/重试…）；纯行为树又缺少对「车辆当前处在什么模式」
这一全局约束的显式表达。

### 关键细节：事件发生 ≠ 一定转移

转移规则带守卫（guard）。例如「请求换道」在目标车道有车时不应生效：

```cpp
addTransition({kFollow, kObstacleDetected, kLaneChangeLeft,
               [](const FsmContext& ctx) {
                 return ctx.allow_lane_change && ctx.left_lane_exists && ctx.left_lane_clear;
               },
               nullptr, "左侧车道空闲，换道绕行"});
```

同一 `(from, event)` 可注册多条，按注册顺序取第一条守卫通过者——这天然表达了优先级。

### 关键细节：换道需要连续多帧确认

单帧的瞬时判断在感知抖动下会产生「换道-放弃-再换道」的反复。
加一个 3 帧的确认窗口是最简单有效的抑制手段。

### 踩过的坑：「车距」到底指什么

传感器给出的是两车**中心距**，而交通语境下的「车距」一律指**净间距**
（自车车头到前车车尾）。两者相差一个车长。

早期版本直接拿中心距去做跟车与制动决策，配置的 `min_follow_gap = 5.0 m`
被当成了中心距。对 4.6m 长的车来说，5m 中心距只剩 **0.4m 净距**——
车实际上已经贴上去了。表现是「看着保持了 5m 车距，实际上追尾了」。

修正方式是在感知层统一换算：

```cpp
const double net_gap = longitudinal - object.length * 0.5 - ego_length * 0.5;
```

修正后前车急刹场景的最小间距从 0（碰撞）变为 4.17m。

这类缺陷的危险之处在于**它不会以异常的形式暴露**：所有数值都"看起来正常"，
量纲也对，只是差了半个车长的常数项。唯一的防线是把语义写进字段名与注释
（`lead_distance` 的文档明确写"净间距"），并在集成测试里用绝对间距做断言。

### 踩过的坑：安全约束不能只依赖单一判据

TTC 在低速下会失真：自车以 0.1 m/s 蠕动、净间距 2.4m 会算出 1.5s 的
「碰撞时间」，但实际上一脚刹车就能停住。因此低速下主动抑制 TTC 是必要的。

但抑制 TTC 之后，如果安全约束**只有** TTC 这一个判据，低速时就等于完全没有
约束——实测中决策层会在距停止前车仅 4.8m 时仍以 11 m/s 为目标加速。

正确做法是让两类判据并存：TTC 负责高速，绝对间距负责低速，
两者共同取最小值。

## 5. 路径平滑与数值优化

### 问题建模

```
min_{P₀..Pₙ}   Σ w_smooth ·‖P_{i-1} − 2P_i + P_{i+1}‖²   平滑项
             + Σ w_dev    ·‖P_i − P_i⁰‖²                  贴合项
             + Σ w_len    ·‖P_{i+1} − P_i‖²               长度项
             + Σ w_curv   · max(0, |κ_i| − κ_max)²        曲率约束（铰链惩罚）
```

三项权重互相牵制：平滑项单独作用会把路径缩成一条直线，贴合项拉住它，
长度项防止路径点向两端聚集。

**长度项不是可有可无的**：没有它时，平滑项会把相邻点越拉越近
（间距趋零不增加二阶差分代价），结果是一串挤在一起的重复点，参数化随之退化。

### 曲率残差用块内中心差分

κ 是三点坐标的有理函数，解析雅可比冗长且极易出错。这里在残差块内部用中心差分。
代价是每次迭代多出若干次残值求值，但对于数十个点的路径完全可以接受，
换来的是实现正确性与可读性——这个权衡在数值优化里通常是划算的。

### 平滑铰链

曲率惩罚用 `0.5·(e + √(e²+ε²)) − ε/2` 而非硬 `max(0, e)`。
硬铰链在 e=0 处梯度不连续，求解器会在阈值附近来回震荡；平滑版本处处可导。

### 外层约束迭代

惩罚法只能渐进逼近约束，单轮固定的曲率权重未必足够。外层逐轮增大曲率权重
（默认 5 轮，每轮 6 倍），以上一轮的解为初值热启动，直到满足约束或达到轮数上限。

### 实测发现：固定端点处曲率无法优化

在带噪声的圆弧路径上，优化后**内部所有点都精确压在 κ=0.0500 的限值上**，
但整体最大曲率仍为 0.058——超标点全部集中在被固定的首末点邻域。

原因很直接：首末点被上下界钉死后，其邻域的曲率由固定点与本就带噪声的原始路径
共同决定，再多权重也压不下去。这是物理上无法优化的部分。

因此报告里单独给出 `final_interior_max_curvature`（排除首末各 2 点），
用它作为验收指标才反映优化器的真实效果。

### 自研 LM 求解器

阻尼按海森矩阵对角元素缩放，使阻尼对各参数尺度自适应。
高斯-牛顿路径无阻尼可调，退化为缩小步长的线搜索。

残差块接口支持**多个参数块**——这是必需的，因为一个平滑残差天然同时依赖
相邻三个路径点，把它们拆成三个独立残差会丢失耦合信息（雅可比里点与点之间的
交叉项全部为零）。

`Problem::verifyJacobian` 用中心差分校验解析雅可比，返回最大相对误差，
是防止雅可比写错的第一道防线。

### 两个平滑后端：B 样条 vs 数值优化

项目实现了两个可切换的路径平滑后端，实测（41 点带噪圆弧，κ_max = 0.05）：

| | B 样条拟合 | 数值优化 |
|---|---|---|
| 最大曲率 | 0.0410（满足） | 0.0544（未满足） |
| 曲率变化率 | **0.0074** | 0.0643 |
| 最大偏移 | 2.298 m | **0.277 m** |
| 耗时 | **2.94 ms** | 420.12 ms |

**这不是"谁更好"，而是两条不同的技术路线：**

- **B 样条**：用 12 个控制点拟合出 C2 连续曲线再重采样。平滑度与速度压倒性占优，
  但曲线是"重新画"的——它不保证贴住原始路点，2.3m 的偏移对 3.5m 宽的车道
  足以导致压线。
- **数值优化**：以原始点为决策变量、最小化"平滑 + 贴合"的加权代价。
  贴合度好 8 倍，但慢两个数量级，且内置求解器压不进曲率约束。

因此 `kAuto` 模式的判据是**偏移**而不是曲率——实测发现 B 样条的曲率本来就容易
满足约束，真正会出问题的是它贴不住路径。

**换上 Ceres 后对比会变**：优化后端变成 0.0505（满足约束）、14.23 ms（只慢 6 倍），
B 样条的优势收窄到只剩平滑度。**后端选择与求解器选择是耦合的。**

### 踩过的坑：实现了却从未被调用的模块

工程里一度存在大量"实现了、单元测试通过、但生产代码从未调用"的模块：
整个 B 样条模块（797 行）、Delaunay/Voronoi 绕障、以及 CurveFit 的大部分函数。
用 `grep` 三十秒就能查出来，而它们的存在会让"我实现了 XXX"这句话失去依据。

**根因不是疏忽，而是测试策略的盲区**：单元测试逐个验证模块自身，却没有任何
一个测试断言"这个模块被主流程用到了"。模块越独立、测试越充分，这个问题越隐蔽。

修正方式是**把模块接进主流程并让它产生结论**——B 样条现在作为可切换的平滑后端
参与对照实验，死代码变成了一个有数据支撑的工程结论。剩下的 Voronoi 绕障仍然
处于未接线状态（它需要障碍物点云，而项目还没有真正的感知模块），这一点在
README 中如实标注。

**教训**：判断一个功能"做完了没有"，标准不是"它能通过测试"，而是"它在主流程里
被执行过"。`grep` 是比测试更早发现问题的手段。

## 6. 速度规划

三个约束共同决定速度上限，取最小值：

- **曲率约束**：横向加速度 `a_lat = v²·κ` 不得超过舒适上限 → `v ≤ √(a_lat_max / κ)`
- **前车约束**：IDM 模型按车头时距跟车
- **舒适约束**：纵向加速度与 jerk 都要有界

### 关键细节：必须双向传播

得到逐点速度上限后，要做**后向传播**（保证在每个点之前都能减下来）
再**前向传播**（保证加速度不超限）。

顺序不能反：先做前向传播会把速度抬到「刹不住」的水平，
后向传播虽然能压回去，但得到的是过于保守的剖面。

## 7. Bag Chunk 压缩

实车 bag 出于存储考虑经常是压缩的，因此不支持解压的解析器实际可用性有限。
rosbag 支持三种 Chunk 压缩方式：`none`、`bz2`、`lz4`。

### 压缩格式的交叉验证

这是本项目里验证做得最扎实的一块。**读写器是自己写的，用自己的写入器验证自己的
读取器只能证明内部自洽，不能证明符合规范。** 因此改为与独立实现双向对撞：

| 算法 | 独立参考实现 | 验证方式 | 结果 |
|---|---|---|---|
| LZ4 | ROS 官方 `roslz4`（`ros_comm/utilities/roslz4`，编译为独立工具） | ① roslz4 压缩 → 本项目解压<br>② 本项目压缩 → roslz4 解压 | 双向逐字节一致；**两边压缩产物大小完全相同**（105058 字节） |
| bz2 | Python 标准库 `bz2` 模块 | ① Python 压缩 → 本项目解压<br>② 本项目压缩 → Python 解压 | 双向逐字节一致；压缩产物大小完全相同（76620 字节） |

「压缩产物大小完全相同」比「能互相解压」是更强的证据：它说明分块策略、
帧参数、压缩级别都精确对齐，而不只是"能读懂"。

### 关键细节：ROS 的 lz4 到底是什么格式

**这一步差点做错。** 直觉上会以为 ROS 用的是 LZ4 的块 API（`LZ4_compress_default`
/ `LZ4_decompress_safe`），因为 roslz4 的源码里确实调用了 `LZ4_decompress_safe`。

但读完整的分帧逻辑后发现：**roslz4 写出的其实是标准 LZ4 Frame 格式**
（magic `0x184D2204`），它自己手写帧解析只是为了不依赖 `liblz4` 的帧 API。
它强制了几个标志位：

```
version                 == 1     (标准要求)
block_independence_flag == 1     (块独立)
block_checksum_flag     == 0     (无块校验和)
stream_size_flag        == 0     (不写 content size)
stream_checksum_flag    == 1     (必须有流校验和)
```

因此正确做法是直接用 `LZ4F_decompress`（帧 API）——它会自动处理这些标志。
若按第一直觉用块 API 自己拼分帧，实现会复杂数倍且极易出错。

块大小索引两边也完全一致（roslz4: `1 << (8 + 2*id)`，LZ4F: `max64KB=4` /
`max256KB=5` / `max1MB=6` / `max4MB=7`），roslz4 默认 id=6 即 1MB。

### 顺带查出的容器层差异：BagHeader 的填充长度

既然官方源码在手，就把容器层的细节也逐条核对了一遍。绝大多数常量都对得上
（`INDEX_VERSION=1`、`CHUNK_INFO_VERSION=1`、chunk_info 的 `(conn, count)` 对、
索引条目的 `(time, offset)` 布局），但**BagHeader 的填充算错了**：

直觉上会认为"这条记录被填充到 4096 字节"，于是写：

```cpp
padding = 4096 - (4 + header_len + 4)   // 整条记录 = 4096
```

而 ROS（`rosbag_storage/src/bag.cpp` 的 `writeFileHeaderRecord`）是：

```cpp
if (header_len < FILE_HEADER_LENGTH)
    data_len = FILE_HEADER_LENGTH - header_len;   // 只减 header_len
```

于是整条记录是 `4 + header_len + 4 + (4096 − header_len)` = **4104 字节**，多出 8 字节。
另外 ROS 的填充字节是**空格**，不是零。

这个差异**不影响读取**——bag 格式是自描述的，读取方只按长度字段跳过——但会让产出的
文件与 ROS 写出的逐字节不一致。修正后实测：

```
header_len=73  data_len=4023  整条记录=4104 字节
填充字节 = b'    '（空格）
```

**这类错误只有读参考实现的源码才会发现**，靠"能读能写"的自测永远暴露不了。

### 实测：bz2 会拖垮整条管道

同一份数据（12.56 MB，700 条消息，含 100 帧点云）：

| Chunk 压缩 | 文件大小 | 管道吞吐 | 相对未压缩 |
|---|---|---|---|
| none | 12.56 MB | 329.49 MB/s | 100% |
| **lz4** | 12.27 MB | **251.43 MB/s** | **76%** |
| bz2 | 11.24 MB | **7.14 MB/s** | **2%** |

bz2 只多省下 1MB，却把吞吐打到 2%。**压缩率与解压开销的取舍在这里完全不对等**：
lz4 保留了 76% 的吞吐，bz2 只保留 2%。

结论：实车数据若追求处理效率应当用 lz4；bz2 只适合归档存储、不需要频繁读取的场景。

## 8. 仿真内核

### 运动学自行车模型

以圆弧**精确积分**而非欧拉近似：

```
θ' = θ + κ·ds
x' = x + (sin(θ+κ·ds) − sin(θ))/κ
y' = y − (cos(θ+κ·ds) − cos(θ))/κ
```

### OBB 碰撞检测

用分离轴定理（SAT）：两个 OBB 各取两条边法向，共 4 条轴，
任一轴上投影不重叠即不相交。

**不能用「中心距减去半径」这类近似**——它会把斜向靠近误判为更远，
在车辆斜向切入时给出错误的碰撞判断。

### 确定性

内核不使用随机数，相同输入必得相同输出。这是回归测试比对的前提。
`test_sim.cpp` 中有专门用例验证同一场景跑两次轨迹逐点完全相同。
